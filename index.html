Real-Time Race Strategy Engine

NASCAR Analytics Team — SportsTech Dynamics

Role: Technical Program Manager
Team: 4 engineers, 2 data scientists
Timeline: 6 months
Stack: Python, AWS, Kafka, TensorFlow

The Problem

Race teams lacked real-time strategy predictions during yellow flag events, causing delayed pit decisions and lost track position. Manual analysis took 45+ seconds — an eternity in racing.

Business risk: Poor pit timing = lost races = lost sponsorship value.

Why This Was Hard

  • Real-time telemetry and historical simulations had mismatched schemas
  • No reliable labeling for ML training data — "good pit decisions" were subjective
  • Stakeholders (crew chiefs) needed explainability, not just predictions
  • Sub-second latency requirements on race day with unreliable track connectivity

What I Did

  • Defined data contracts between telemetry, simulation, and ML teams
  • Built labeling framework with domain experts to create ground truth dataset
  • Drove architecture decision: edge inference with cloud fallback
  • Ran weekly stakeholder syncs translating model confidence into actionable UI
  • Managed vendor relationship for track-side connectivity backup

Outcomes

40%
Faster decisions
6
Races deployed
92%
Crew chief adoption

What I Learned

Explainability beats accuracy for user adoption. We had a better model that crews didn't trust. Simpler model + clear reasoning won.

Enterprise Data Lake Migration

Data Platform Team — GlobalRetail Corp

Role: Technical Program Manager
Team: 8 engineers, 3 teams
Timeline: 9 months
Stack: Databricks, Snowflake, Airflow, dbt

The Problem

Legacy data warehouse was hitting scale limits. Query times ballooned to 20+ minutes. Data teams were blocked, and leadership was about to approve a $3M hardware upgrade that wouldn't solve the real issue.

Business risk: Analytics backlog growing 40% quarterly. Product decisions delayed by weeks.

Why This Was Hard

  • 150+ downstream dashboards with undocumented dependencies
  • Three teams with competing priorities and no shared roadmap
  • Zero downtime tolerance — migration had to be invisible to users
  • Political: legacy system owner resistant to change

What I Did

  • Built dependency map using query logs — found 40% of dashboards were orphaned
  • Created migration scorecard tracking data quality, performance, and cost per table
  • Designed dual-write pattern for zero-downtime cutover
  • Ran weekly "migration war room" syncing all three teams
  • Negotiated with legacy owner: positioned as "modernization" not "replacement"

Outcomes

$2M
Annual savings
8x
Query speed
0
Production incidents

What I Learned

The technical migration was 30% of the work. The other 70% was dependency mapping, stakeholder alignment, and managing the politics of sunsetting someone's system.

LLM-Powered Support System

Internal Tools Team — CloudScale Systems

Role: Technical Program Manager
Team: 3 engineers, 1 ML engineer
Timeline: 4 months
Stack: OpenAI API, RAG, Pinecone, React

The Problem

Internal support team drowning in repetitive tickets. 60% of questions were answered in existing docs — but nobody could find them. Support response time: 4+ hours average.

Business risk: Engineering productivity loss estimated at $500K/year from waiting on internal support.

Why This Was Hard

  • Documentation scattered across Confluence, Notion, Slack, and tribal knowledge
  • LLM hallucination risk high — wrong answers worse than no answers
  • Security review required for any tool touching internal data
  • Skeptical users burned by previous "AI" tools that didn't work

What I Did

  • Scoped MVP: 50 most common ticket types only — resist feature creep
  • Built confidence scoring: AI only answers when >85% confident, else routes to human
  • Drove security review — got approval by limiting data scope and adding audit logs
  • Ran 2-week beta with power users, iterated on prompt engineering
  • Created feedback loop: thumbs up/down on every answer feeds retraining

Outcomes

70%
Ticket deflection
10K+
Monthly queries
4.2/5
User satisfaction

What I Learned

The "I don't know" feature was the most important. Users trusted the system because it admitted uncertainty instead of confidently hallucinating.

API Gateway Consolidation

Platform Engineering — FinTech Innovations

Role: Technical Program Manager
Team: 6 engineers across 4 teams
Timeline: 5 months
Stack: Kong, AWS API Gateway, Terraform

The Problem

12 microservices, 12 different auth implementations, 12 different rate limiting approaches. Security audit flagged 3 critical vulnerabilities. Every new integration took 2+ weeks of custom work.

Business risk: Security exposure + integration velocity killing partnerships.

Why This Was Hard

  • Each service owned by different team with different priorities
  • No one wanted to be "first" to migrate — risk without reward
  • Legacy auth tokens embedded in partner integrations
  • Zero budget for new headcount — had to do with existing teams

What I Did

  • Built business case: quantified security risk + integration delay costs for leadership
  • Designed "migration sprints" — each team gets 2 weeks of dedicated support
  • Created compatibility layer for legacy auth during transition period
  • Published migration playbook so teams could self-serve
  • Tracked adoption weekly — celebrated early adopters, applied pressure to laggards

Outcomes

99.9%
Uptime achieved
12→1
Auth systems
2 days
New integration time

What I Learned

Platform migrations are adoption problems, not technical problems. The compatibility layer bought us time. The migration sprints created accountability. The playbook scaled knowledge.
